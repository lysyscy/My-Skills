# 技能维护与反馈沉淀

收到真实业务反馈时使用。目标是修正可复现的问题，并保持下一次能找到、理解和执行规则；本次业务决定由本次工作簿承载。

## 规则归属

| 层 | 唯一职责 | 何时修改 |
|---|---|---|
| SKILL.md | 触发、项目/地址确认、形态路由、共用底线、必要参考入口 | 所有任务都必须知道的边界或读取条件改变 |
| A/B处理参考 | 各形态的复原、分类、合并、排序方法 | 对应处理方法改变 |
| 供应商外发与内部复核 | 信息去向、供货边界、成套关系、原清单去向、待办及验收 | 外发与内部职责或闭环改变 |
| 询价单模板规范、assets | 列结构、标题、公式、冻结与打印；assets是通用空白模板 | 表格契约改变，按实际派生关系同步 |
| scripts | 确定性、可重复的机械处理与验证 | 规则明确且确需自动执行；案例脚本须注明适用范围 |
| 本次任务文件 | 项目、地址、源行、数量、未决项、决定及真实验证证据 | 当前业务更新；不复制进通用技能 |

一个规则只保留一份权威正文，其他位置用带触发条件的引用。维护用参考按需加载，不加进每次业务操作必读路径。新文件有独立职责才建，新增后必须从适当入口可达；既有分类无法容纳时再扩展，避免为每次反馈创建一套平行规则。

## 反馈处理

1. 用实际文件、源行或操作重现差异，确认预期及已有用户决定；区分执行偏离、规则缺口、工具限制和单次业务取舍。明确授权内直接修正，只有仍缺业务判断才问用户。
2. 执行偏离先修产物与执行位置，规则已有就不重复加禁令。规则缺口更新上表对应主人；单次取舍留任务，用户明确要求通用化或事实支持通用机制时才提炼。
3. 改写过时正文并核所有实际引用、脚本/模板消费者，消除相反旧说法；入口只加必要导航。保留历史证据，历史案例不自动升级成新默认。
4. 每条新规则说明触发、处理、例外及可观察完成条件；用本次失败样例验证修复，再核最近相关正反例。纯文档维护核引用与行为契约；代码或模板改变才扩大相应检查，未变的有效证据复用。
5. 在已授权的维护源修改，经现有版本管理、验证及分发流程更新中央库，核实际部署内容并保持技能身份、预设和部署选择。不会用直接改Agent副本代替维护源。

## 本次反馈对应的验收例

- 全量去向表存在且源记录不减；新增待办不是替换去向表。
- 内部表头在第3行时冻结A4，滚动后前三行保留、数据行可滚动；供应商第2行表头继续按自身模板冻结。
- 同一问题有事实、推荐、来源和状态；已确认的处理不重新提问，资料仍缺则只留剩余待办。
- 修改“两张内部表”的契约时同步旧“仅最后一张内部表”引用，供应商表中仍无内部信息。

以后出现新反馈时按其所属规则与受影响消费者更新，已有验收例只保留仍有保护价值的最小集合，不逐轮追加整段会话。
