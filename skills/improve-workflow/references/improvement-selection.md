# 候选归属与外部能力

读者：执行 improve-workflow 的 Agent。候选来自实际会话、差异和反馈；本文件拥有优化选择方法，实施节奏仍回 implement-solo-spec，项目绑定回 setup-solo-workflow。

## 先提炼原因，再确定主人

把观察写成“触发条件 → 原机制为何失效 → 要改变的行为 → 能检出原问题的反馈”。对耗时、错误或用户介入追查直接原因，主动考虑改进，保留无须改规则的结论。

“执行偏离”是现象分类。结束归因前核实际入口是否触达、指令在该场景是否明确且可操作、相邻规则的优先级与决策责任是否一致、失败能否及时被反馈检出。仅证明文字已写，不能判定机制足够；一次真实失败也能揭示歧义或冲突，次数用于佐证。无须修改时，说明实际可用的原机制、此次失效原因及恢复反馈；证据不足则保留待判定。

| 证据与判断 | 处理与落点 |
|---|---|
| 核实原指令清楚、可达、可操作，仍未执行 | 在原主人处修实际失效的入口、反馈或约束；偶发操作失误且现有反馈已检出并完成修复时保留证据。发现歧义、冲突或责任缺口则修原规则，避免另加同义提醒 |
| 去掉仓名、业务常量和本机路径后，触发条件与解决机制仍适用于另一种项目 | 可提炼为个人方法；现有同义规则先合并。接入缺口回 setup-solo-workflow，实施/验证/审查缺口回 implement-solo-spec，复盘/选择/包维护缺口回 improve-workflow |
| 必须依赖本仓业务、框架接口、执行器选项、服务现场或授权才能成立 | 回项目既有业务权威、配置、检查、约束或待办；机械问题优先确定性检查，入口只留条件指针 |
| 一个发现同时含通用方法与项目能力缺口 | 分开处置：个人包维护方法，项目维护实现与例外；分别核授权和验收，项目动作未完成时据实留待办 |

一个项目的证据可以揭示通用机制，但须说明可迁移的依据，不能把样本数当充分证明。候选完成条件是原因、主人、动作和反馈明确；没有动作价值、证据不足或已有机制足够时说明结论，不要求每次都有两类改动。

例如“大场景调试小问题”：最低成本反馈的策略回实施技能；某仓执行器只能选整组，则在该仓处理用例拆分与选择能力。个人方法不保存该仓命令、数据量或固定超时。当前只授权改技能时，项目候选留建议；如已有项目待办记录授权，则按其协议留指针和下一步。

## 按需能力选择

实际缺口读取 [capability-selection.md](capability-selection.md)，这是唯一选择正文，不启动完整复盘。

## 复盘中的长期采纳

improve-workflow 从实际失败与成本提炼原因、判断可迁移性与长期收益；复用 capability-selection.md 的选择方法，不重复搜索和小场景证据。单项目能力留项目，共用方法回所属个人技能；setup-solo-workflow 仅负责必要项目绑定。外部原版由原渠道维护，个人包只维护必要适配和引用。

普通实施中的按需查阅不启动整轮复盘。维护任务采用 implement-solo-spec 统筹时，该技能负责依赖、分派、整合、累计验收与唯一最终双轴；improve-workflow 负责冻结版本、隔离修改、包核验、发布及同步。主 Agent 统一共享写入与发布，复用覆盖相同版本和范围的审查及收尾证据，必要包检查继续保留。
