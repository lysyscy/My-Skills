# 软件更新

## 按请求选模式

| 请求 | 动作 |
|---|---|
| 检查软件更新 | 严格只读。使用无写入副作用的查询，在对话交付结果。默认不写报告、状态或记录，不刷新看板。 |
| 检查并记录 | 完成只读检查后，按[记录规则](references/completion.md#记录)使用调用方声明的入口。 |
| 讨论更新 | 核对证据、解释影响，在对话中更新候选和待确认事项。等到明确的执行指令再应用。 |
| 对本批说「开工」「开始」「全更新」 | 执行本批已就绪且在授权内的候选。先补核已有确认。刚讨论的几项不缩小整批范围。 |
| 更新指定项或续跑 | 按指定项或原批授权范围执行。接续前核实际状态和基准，复用仍有效的验证。 |
| 更新收尾 | 按[收尾规程](references/completion.md)完成本批选定的检查，处理获准的迁移、清理和记录。 |

## 三个契约

- **Local Inventory & Fact Gathering（本地清单与事实采集）**归调用方。读取可用的清单及采集说明，沿其范围、暂停标记和只读入口核查。缺少清单或采集入口时，按用户指定或当前工作范围只读检查，在对话汇报。
- **Observed State（观测状态）**按本批检查范围分别记录四层证据。写当前值、来源和核对时间。应查但缺证据的层标「未验证」。
  1. 声明或锁定的版本。
  2. 磁盘上实际安装的版本及环境。
  3. 运行进程实际使用的版本。
  4. 宿主重载或部署后，目标消费者实际加载的版本。
- **Batch Plan JSON（批次计划）**是 [离线报告生成器](scripts/render_report.py) 的唯一输入契约。需要且获准写 HTML 报告时，按[报告契约](references/reporting.md)提供独立快照。

## 检查候选

1. 每个目标分别核组件新版和当前版本的依赖新版。查实际消费者、声明与锁的归属、同渠道官方发行及兼容约束。共享环境同时核相关消费者，注明直接和传递依赖的覆盖范围。
2. 在有效约束内选择可独立更新的最新稳定版。上游精确 pin、发行锁和捆绑依赖沿上游渠道维护。对自有 pin 查新版并标明需要调整的值。按调用方的等待期和预发布约束标明暂不可用或必需预发布的候选。
3. 为候选固定编号、精确版本、来源、拟应用环境、最小检查和提交或锁基准。分别说明两类检查的结论、证据缺口和待确认事项。完整检查且无适用候选时才写「确认无更新」。

## 验证与应用

1. 核对本批快照、有效确认和当前基准。目标或基准变化时先复核影响。缺外部条件或授权的候选留待办，继续处理其他独立项。
2. 按[检查范围](references/completion.md#选定本批检查)选择最少的检查，定下做到哪一步就结束。需要隔离演练时，分别写清演练和正式应用的目标环境。
3. 用调用方声明的安装、同步或部署入口应用已满足前置条件的候选。部署、服务启停、共享环境切换和数据写入分别核授权。应用异常时核实际状态，再按维护规程重试或回退。
4. 按[更新收尾](references/completion.md)取证，对照本批编号交付实际结果和待办。未加载或待验收的项保留对应状态。
