# 软件更新

| 用户动作 | 本轮入口 |
|---|---|
| 检查软件更新 | 走[只读检查](#只读检查)，生成本地 HTML 报告。 |
| 检查并记录 | 先只读检查，再更新[状态与记录](references/status.md)。 |
| 询问、讨论或确认更新方案 | 只核对事实和方案，记录确认结果；执行等开始指令。 |
| 在更新对话中说「开工」「开始」「全更新」 | 走[验证与应用](#验证与应用)，默认执行本批全部可更新项。 |
| 明确要求只更新指定项，或继续已开始的批次 | 走[验证与应用](#验证与应用)，沿明确范围或原批范围执行。 |
| 升级后验收、迁移入口、清理残留 | 走[更新收尾](references/completion.md)，沿用仍有效的验收证据，只处理已授权目标。 |

先用[项目与工具链](references/targets.md)定位项目和消费者，按目标读取 [UniGetUI](references/unigetui.md)、[Hindsight、AstrBot 与受管技能](references/services.md) 的对应分支。项目自己的入口负责兼容性验证、服务加载和发布。

**汇报与记录**。每次检查生成一份可离线打开的本地 HTML 报告。对话交付链接与本批要点。应用结果用 Markdown 表格逐项列实际版本、适配和待办。交付前按[汇报格式](references/reporting.md)核列。版本状态与批次记录见[状态与记录](references/status.md)。本技能唯一维护源为 `D:\dev\My-Skills\skills\software-updates`；获准回写时修改该源的记录，再按 My-Skills 发布流程同步。中央库和各 harness 安装副本供读取，不作为另一编辑源。项目当前规则和服务实况仍由各自项目持有。

## 依赖选版口径

先从实际运行、构建或维护入口确认依赖的消费者和有效约束。**对可独立更新的依赖，默认选上游约束内可用的最新稳定版本**。上游发行的精确 pin、发行锁及捆绑依赖沿上游渠道维护。已核实没有允许且能生效的更高版本时归「无需更新」。外围锁变化在确认有实际消费者后才列为候选。**自有项目的精确 pin、本地生成的锁是当前基准，仍要检查新版稳定依赖**；在临时候选输入中评估更新该 pin，保留已确认的项目、平台、宿主和兼容性限制，有候选时标「需更新本地 pin」。归属不明时标「待确认」。候选默认选稳定版；上游要求的预发布依赖单列原因和版本，独立于稳定版候选计数。

## 只读检查

1. **组件新版**。先按[检查范围](references/targets.md#检查范围)排除暂停或退役目标。未点名时覆盖其余已登记项目、工具和专项，并单列 UniGetUI。分别核声明或锁、实际安装或运行、同渠道官方发行版本。以运行证据确认加载，以安装证据确认磁盘。每个来源记录核对时间。
2. **当前版本的依赖新版**。无论组件本身有无新版，默认同时核对其当前版本的依赖声明、发行锁、本地锁和实装，按上述选版口径查询约束内的最新稳定版。共享环境把本体、已启用插件和实际附加消费者的约束联合解析；依赖图包含受影响的传递依赖。解析在临时目录进行，形成候选版本与实装的差异；只查了直接依赖时明确标出覆盖范围。仅随组件发行包捆绑、缺少独立安装入口的依赖写明更新渠道和核查边界。
3. **逐项交付两类结论**。表格分别列组件新版检查和当前版本依赖检查。只有对应检查完整且无候选时才写「无候选」。未查到、扫描未完、来源不可达、解析失败、仅部分依赖可查均在对应格写明原因和范围。为候选固定编号、精确版本、来源、拟应用环境和基准提交或锁 SHA-256，标「可进入验证」「待确认」或「按专项规程」。能查证的事实自行核对；需用户决定时，简要说清原因、影响、选项和推荐。讨论中确认的选择用于修正本批候选，等用户明确开始才执行。
4. **只读与记录**。使用锁文件、实装元数据、只读运行探针和上游查询；依赖解析只写临时输入与候选锁，使用现有解释器并避免隐式同步、改正式锁或下载解释器；正式声明、锁和环境的变动按更新授权执行。默认交付本地 HTML 报告和对话摘要，用户明确要求记录才回写，无变化的检查不追加历史。用户明确要求演练时，按现有锁在隔离环境演练并标明。

## 验证与应用

1. **固定本批**。在软件更新对话中收到「开工」「开始」或「全更新」，以本批完整报告及讨论中的确认结果定范围：纳入全部可进入验证的候选，包括已确认并补齐条件的项。只有用户明确限定范围时才缩小；刚讨论的几项不构成范围限制。固定各项编号、精确目标、安装来源和验证基准，用户已处理的项核对实际结果。版本或基准变化、验证失败或网页列为「待确认」「按专项规程」时，先自行复核并按对应规程排查。只有仍缺外部条件、用户决定或补充授权的项才留待办；继续做完其他独立项。无法定位本批时重新列候选。补充授权后从停点接续，复核基准、目标和证据，复用仍有效的验证。已验证的候选标「候选通过」，直到同步、部署或加载有各自的证据。
2. **验证候选**。新装或刷新依赖时，按上述依赖选版口径固定已核渠道的最新兼容稳定候选。改自有项目精确 pin 和本地锁仅限已选目标；换解释器或复现时沿用原包锁。在隔离环境生成并按候选锁安装，核锁差异、实装和受影响的传递依赖。用项目正式验证入口和合成或已获准隔离数据。无法在隔离环境验证的功能保留待验。
3. **按授权应用**。一次选择可覆盖符合条件且目标已登记的独立开发同步。生产部署、服务启停、业务数据、共享工具切换和技能分发按本批核授权。执行前复核来源、差异、并发、消费者、验证和回退点。某项仍需授权或条件未满足时先记下，继续完成独立项目。把各项目确实需要用户决定的事项集中到批次末尾一次提出，逐项给出影响和推荐。专项依照 [UniGetUI](references/unigetui.md#逐项更新)、[服务与技能](references/services.md) 或[工具链迁移](references/targets.md#工具链与项目迁移)。
4. **复核并收尾**。按[更新收尾](references/completion.md)完成实际加载与必要功能验收、受影响入口迁移和残留处置。切换或核验失败按项目回退并复验；恢复未知时保留现场。最终答复前按[更新对账](references/reporting.md#更新)逐项核对本批原始 HTML，主动交代所有未完成项。回写已授权尝试的结果，成功且有变化的批次记一行，异常补原因、证据和待办。证据用项目已采用的运行区保留，按项目规则关闭本批资源。
