# 专项文档迁移

用于跨任务、归属不明或改变长期资料结构的专项治理。普通已授权改动及阶段收尾中的直接相关合并、删除、消费者修复由 execution 和 document-maintenance 执行，不另启动迁移审批。

先只读建立迁移清单：旧位置、内容类别、独有有效信息、目标权威、活动引用、机器消费者、归档/删除的独立理由及恢复依据。现行目标采用 [document-layout.md](document-layout.md)；不按年龄判有效性，不把垃圾全部搬入 archive。

用户确认整体清单后可以批量执行，不逐文件重复询问。超出清单、含独有信息、仍服务活动工作或归属不明的材料，先保护，不擅删。

正在运行任务的业务范围、验收及外部操作权限保持固定；已明确批准的治理切片可受控采用，在原规格记录来源、范围与切换点，并实际读取安装后的相关规则，不另建版本账本。迁移必须保护未提交内容、未跟踪附件、intent-to-add、索引以及可恢复证据。旧路径过渡指针只能在实际消费者仍需要时存在；退出条件满足后退役，不永久用映射假装统一。

完成意味着：现行权威实际统一、独有信息未丢、活动工作可接续、引用与机器消费者通过必要验证、历史可追溯、剩余例外和保存状态真实。没有达成的条目明确保持未完成。

## 迁移步骤

专项任务按以下程序执行；当前请求已有明确整体授权和清单时复用，不重复询问。

| 阶段 | 动作与产物 | 授权及停止条件 |
|---|---|---|
| A. 固定现场 | 记录 Git 基线、工作区和索引、未跟踪/intent-to-add 文件、活动任务及实际消费者；保护原件 | 初查只读；不 reset/clean，不从“未提交”推出可丢弃 |
| B. 建立清单 | 对每份相关材料写旧路径、内容类别、独有信息、目标路径、活动引用/机器消费者、保留/归档/删除建议 | 只对本项目可见资料下结论；不凭年龄判定有效性 |
| C. 提炼权威 | 为每项仍有效事实确定唯一现行主人；活动范围/历史过程/无价值副本分开 | 业务定义冲突须裁决；技术路径按本标准独立选择 |
| D. 提交整体方案 | 呈现迁移、引用修复、删除候选和可恢复依据 | **用户确认整体方案后才执行**；不逐文件重复问；超出清单的新独有材料不擅删 |
| E. 迁入现行路径 | 先建立有真实内容的标准位置，修必要指针和消费者，再退役旧现行正文 | 对活动 effort 不同时切换语义和运行基线；可先等待该批结束 |
| F. 处理历史与垃圾 | 有效独有知识先归现行主人；Git可追溯且无活动用途的原件删除，具名历史例外与非Git证据按各自生命周期保存 | 无授权、未知来源、仍有活动用途或唯一失败证据，暂留并说明 |
| G. 验证与保存 | 检查内容守恒、活动任务、真实消费者、链接、差异、保存范围；按项目授权提交/推送 | 无远端仅跳过推送；没有测试证据就不报迁移完成 |
| H. 退役过渡指针 | 活动任务不再消费旧路径、现行引用及机器范围修正、恢复依据可用后删除兼容指针 | 达不到条件则仍是“迁移中”；永久例外必须有外部约束理由 |

迁移清单可以是当前 effort 的一张表，不要求另建全局登记册。删除候选和归档候选分别列，不把“整体同意迁移”解释为可以任意清空历史。

### 7.3 机器消费者不只看链接

移动文件后，同步核对实际工具中的输入路径、glob、扫描根目录、排除范围、生成配置、校验基线和产物引用。Markdown 链接存在只能证明目标存在，不能证明脚本仍扫描它，更不能证明 Agent 会在正确时机加载它。

遇到工具把旧路径硬编码为接口时，优先改该项目真实配置/消费者并做有针对性的验证；必须保留兼容位置时只留指向新权威的薄入口。若工具确实要求独立生成文件，该文件要明确为派生物，不能人工双写两份权威。

### 7.4 在途任务保护和回滚

正在运行的任务保持业务、验收及外部操作授权基线；治理规则仅在具体切片获批、原规格记录且实际读取后切换。新标准不能将其已批准的统筹模式降级，也不能把旧规格解释为新范围。旧资料可以在活动任务完成后再迁，或者经整体批准由一次受控批次同时改任务引用与消费者。

回滚依据至少覆盖：迁移前版本、未提交原件、索引状态和新旧对应关系。回滚仅还原本次拥有的变更，不使用全仓 `reset --hard` 或无差别清理抹掉并行工作。发现原路径已经出现别人的新内容时，停止该冲突项并保留双方，不自动覆盖。

**完成标准不是“文件都进 archive”。**现行权威已在标准位置；独有有效事实没有丢；活动工作及必要历史能追溯；相关机器消费者真实可用；旧入口不再参与普通路径；剩余例外和未决项明确；保存状态真实。

清理被策略拒绝时保留原目标、失败证据与后续条件，不换工具或删移父目录绕过。
