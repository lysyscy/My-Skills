# 文档维护约定

跨项目方法的维护源。setup-solo-workflow 接入时读取；普通执行者在项目入口要求生成、修改文档或任务收尾时读取。项目已有同等规则时直接读原主人，项目适配仅记录具体落点与必要例外。

## 权威与读取

Agent文档按稳定程度组织：目的、适用边界、术语和长期规则在前；操作约定随后；易变的任务状态、本机信息、日期和运行记录在后。同一用途内先放稳定定义，再放变化内容。入口保留稳定的条件指针，状态和环境事实回各自主人，避免在前部重复动态信息。

既有文档的核心用途和必要导航继续有效：状态页直接提供当前状态，Agent用稳定指针定位其章节；不为排序把所需信息藏起来。修改受影响章节时调整结构和引用，逐次接入，不将普通写作扩大为全仓重排。保持无需变化的前部文字、顺序及引用稳定，不为缓存加长文件。

这种结构增加可复用前缀的机会；实际缓存还取决于宿主拼接顺序、缓存边界和读取方式，不能仅凭文档排序声称命中率提高。依据见[OpenAI提示缓存说明](https://developers.openai.com/api/docs/guides/prompt-caching)。

项目入口用“触发条件 → 权威位置”提供导航，按当前动作读取命中章节；找到权威、更新落点与同批引用后停止扩读，后续只补缺口或变化。当前工作指向在做的规格和票，历史资料按追溯问题查。已读资料复用，入口保持短。

每类事实只有一个维护位置。现行需求以用户确认的业务权威为准，维护在稳定的活位置；effort 规格与票记录各自范围、独有判据和证据，并引用业务权威。使用编号时引用并读取原句。已有需求文档直接复用；尚未澄清的新项目先约定一处简短需求文档或 README 章节的落点，有真实内容时再建立。历史 effort 规格不能代替现行业务入口。测试命令、路径与选项优先查配置，文档保留配置无法说明的操作约束和原因。

活待办和交接中的业务事项只写编号或权威指针、当前状态与下一步，不复制或改写需求正文、业务边界和验收细则。简短事项名称可以保留。历史修订可记录当时裁定，明确其来源与适用范围，供后续追溯。

## 新资料与落点

写之前先判断用途，复用已有主人；只有现有文件无法承载独立用途时再新建。

| 用途 | 维护方式 | 项目需要提供的绑定 |
|---|---|---|
| 跟随产品或进度变化的现行资料 | 原地维护，其他位置用指针；已实现、未实现和待裁定据实区分 | 每类资料的主人与当前工作入口 |
| 记录当时事实与裁定的历史资料 | 保留历史，后续修订追加来源及取代指针；票状态和验收按项目协议更新 | 票、变更记录或决策记录位置 |
| 一次任务中的计划、调查和交接 | 留在该任务范围，仍需继续的工作保持可见；用完按项目既定归档协议封存 | 活动任务位置、归档位置与授权边界 |
| 一次运行的日志、截图和临时文件 | 放项目已有的运行产物位置，保留必要失败证据；释放本任务拥有的临时现场 | 产物位置、忽略与保留方式 |

上述用途不强制每项目都建四套目录。复用现有布局；资料规模很小时在同一文件用明确章节承载。临时运行产物不默认进入正式文档或版本库。

## 实施与同步责任

实现者同步被本次改动弄过时的活说明、注释和指针；收尾前完成同步，再按最终代码及文档输入核验证据有效性，交付实际验证结果。主 Agent 整合时核共有入口、逐条验收与任务状态。使用者无需另开整理任务提醒 Agent 完成这些工作。

改一个事实时定位其主人与相关引用，修改现行说明；需要历史修订时追加来源。受影响的活待办已有需求正文副本时，将该副本收为权威指针，不再随权威一起改写。更新范围跟随本次改动，先用项目已有的定向查询定位副本，普通功能修改不因此扩展成全仓审计。新增目录、搬移或封存遵守已确认的项目协议与当前授权。

例如，用户修订 `docs/product.md` 的 `FR-02` 时，业务边界写在该定义中；活待办只保留“FR-02（见 `docs/product.md`）：已确认、未实现；待独立拆票，当前票范围不变”。历史票如需记载这次修订，按票协议追加来源与适用范围，保留旧记录。

同一资料由一个负责人写入；并行任务把共有入口交主 Agent 整合。收尾逐条对照本次验收、证据实际覆盖范围与未决裁定，再按项目协议更新完成状态；验收缺项或影响验收的裁定未解决时保持未完成，并明确下一步。实现、验证、部署与归档分别据实记录。整个任务验收与必要记录完成后再封存，其导航退出活动清单；仍有未决工作则保留有效活动入口。历史能追溯，与其他任务共享的资料据实保留。

验收与审查证据各在现有主人处保留一份；交接和短索引只留范围、状态、未决事项与指针，不重复测试输出或逐轮过程。只有跨会话或未决接续需要才写短交接。归档缺少必要授权时，完成其余工作并留下具体剩余操作及原因。

按项目协议完成保存与同步，核实际结果。项目允许Git记录或交付消息承载最终同步证明时，用它们报告最后一次提交与推送，不仅为记录回执自身SHA反复生成新提交；必须落盘的回执按项目绑定处理。源码完成、运行加载、现场验收仍分别记录。

收尾处置本任务拥有的临时现场：先确认必要日志、截图和失败复现证据已保存在项目已有产物位置，且证据指针仍可访问，再停止本任务启动的临时服务并清理已无用途的副本及临时文件。为未决复现保留的现场，在现有票或交接中说明用途、位置和下次处置时机；共享或归属不明的现场保持原状。交付据实说明已清理或仍保留的必要现场，不另建清理台账。

清理失败或被环境策略拒绝时，按实际拒绝边界处置；没有获准的安全方式则保留原目标，在已有记录说明动作、目标、实际原因（未提供时注明）、证据位置与后续处置条件。被拒动作不通过更换工具或删移父目录重做；交付分别报告验收与现场残留，验收通过不代表清理成功。

## 核验与用户参与

Agent 收尾核本次新增或改动的指针、落点、失效说明及未决状态，运行项目已有的相关便宜检查；没有机械检查时读取实际文件核对。机械检查证明它覆盖的确定性问题，权威位置和实际含义由聚焦核验判断。失败处理及证据复用按 [implement-solo-spec 的“验证与失败处理”](../../implement-solo-spec/SKILL.md)；沿用现有票及证据位置，不为文档维护增加逐票完整两轴审查、全仓扫描或报告体系。

交付围绕用户关心的结果：实现了什么、如何打开或人工验证、必要风险与需要用户决定的事项。目录命名、资料同步、按约定收尾由 Agent 处理；用户负责需求口径、实质范围、必要授权及人工验收。用户发现的问题进入正常修复流程，不承担整理 Agent 工作记录的责任。
