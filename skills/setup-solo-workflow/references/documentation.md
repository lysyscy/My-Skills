# 文档职责与读取入口

建立、重构文档体系，或发现内容职责混杂时读取。本参考拥有文档的读者、权威与内容分工；物理落点、运行产物和退出动作归 [document-layout](document-layout.md)，日常变更归 [document-maintenance](document-maintenance.md)。普通修改已有且职责清楚的正文，不重新设计整套体系。

## 从读者的实际问题开始

先找到已有正文、入口、生成源和真实消费者，再决定保留、修指针、拆分或迁移。入口按读者动作一次选到负责该任务的正文，正文提供可执行的步骤、必要条件与成功判据；同一概念的规则和必要例外共置，独立分支和查询细节再链接披露，避免执行中反复返回入口找下一条规则。源代码、配置和工具帮助也是权威，能直接查得的细节不另抄清单；文件名齐全、链接可达或篇幅变短不证明可用。

技术文档借用 [Diátaxis](https://diataxis.fr/) 的四种读者需要：

| 读者的问题 | 内容形态 | 完成依据 |
|---|---|---|
| 我还不会，带我练习一次 | 教程：引导学习，用可重做样例获得可见结果 | 新手能完成学习目标；样例不要求真实业务写入 |
| 我知道目标，怎样完成这件事 | 操作指南：目标、前提、步骤、必要分支与成功判据 | 熟练使用者能完成任务，操作权限和危险条件在动作前可见 |
| 字段、选项、接口或格式是什么 | 技术参考：按对象组织准确事实、约束和短例子 | 能直接查到定义，不从教程或事故流水猜参数 |
| 为什么这样、概念怎样联系 | 解释：背景、原理、关系和取舍 | 能理解理由及边界，不把候选方案误当现行事实 |

按主要问题组织正文，短说明可以分节，较长的异类内容通过链接披露。操作所需的警示与简短理由就地保留，不为分类隐藏保护。已有架构/领域说明可以承担解释，无需另建同义目录；有入门需求才写教程。不预建四象限空结构，也不把政策、票、日志硬归技术文档。该裁剪遵循 Diátaxis 的[小步采用](https://diataxis.fr/how-to-use-diataxis/)；下面的文件名与工程落点是本地消费约定，不是业界强制标准。

## 先确定权威，再安排入口

| 资料 | 唯一职责与读取条件 |
|---|---|
| README | 项目目的、边界、使用和稳定导航，供首次进入者定位；不承担完整业务规则或运行回执 |
| AGENTS | Agent操作边界和按动作读取的指针；必要保护在危险动作前可达，不常载全部业务与方法 |
| CONTRIBUTING或既有开发指南 | 开发维护的输入、验证、保存与分发边界，详细命令/操作链接配置或指南；普通业务不自动加载 |
| CODING_STANDARDS或既有规范 | 项目编码约束、作用范围和专题指针；实现前读受影响规则，审查时收齐适用来源；机械要求归实际配置/检查 |
| docs/agents/workflow | 个人方法来源/固定版本、宿主与记忆绑定、项目例外及实际机制指针；不重复贡献指南 |
| issue-tracker / domain / triage-labels | 分别持有已采用的票协议、领域文档消费关系、实际标签映射；按操作读取，没有需求不创建 |
| requirements | 当前已确认行为、范围、业务口径及明确未实现的目标；实现状态与规范效力分开，不能由现有代码反推授权 |
| architecture | 当前结构、重要关系、场景和非显然约束；按下节区分现状、目标及决定理由，引用需求而不复制 |
| guides | 面向真实任务的操作指南；长原理另链解释，完整参数/格式另链参考。有真实学习需求时可在既有docs/guides中另页标明教程目标，或复用项目现有教程入口，不为四类形态预建目录 |
| reference | 项目内技术契约、接口、schema、格式等精确查询资料；外部来源就近引用，不作为未分类资料桶 |
| GLOSSARY / GLOSSARY-MAP | 已确认领域语言及真实多上下文关系，不写实施计划或运行流水 |
| ADR | 一项重要决定的上下文、决定、状态和后果；记录理由和替代关系，不承接普通修复日志 |
| spec / 票 | 本次从哪个基线变到什么、验收、依赖、进度与授权；引用现行权威，不复制整套需求 |
| status / 交接 | 当前活动范围、阻塞、版本与下一步的必要导航/聚合；票状态和原运行记录仍在其主人处 |
| research / 外部调查 | 问题、来源、适用性与未决判断；未采纳内容不成为正式规则。稳定结论进入所属正文并保必要来源 |
| 运行证据 | 指定版本、输入、环境及范围下实际观察；不替代规范或未来状态。位置与保留规则归document-layout |

这两个常见根入口按实际内容采用，已有同职责指南足够就复用；无独立内容不建空壳。架构、业务和界面专题保留主人，根入口不能吸收所有正文。技能或组件独立分发所需的规则、格式、脚本及参考继续随包携带；项目根只导航维护，不让独立消费者依赖作者仓库。机器读取的标题、路径、glob、抽取和生成关系属于真实接口，迁移与消费者切换同批验证。

## 架构与重要决定

借 [arc42](https://docs.arc42.org/home/) 的视角检查本次需要说明的系统边界、主要构件、运行交互、部署、横切机制、质量目标与风险；已有需求、术语和决定用指针复用。只补无法低成本从实现理解且值得维护的知识，不要求十二章齐全、UML或每个小模块都有说明；这是采用相关视角，不是完整套用模板。[官方可选性说明](https://faq.arc42.org/questions/B-1/)

架构入口保系统概览、关系和按动作到专题的导航；长篇正文按真实读者任务拆到同名目录，保必要跨主题约束。当前实现与已接受但未实现的目标分别标明范围与状态；历史设计提案保原义，实施后把有效当前知识更新到现行主人。具体实施步骤和批次归本次规格/票，不混入现行结构说明。

重要决定采用 [Nygard ADR](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions) 的上下文、决定、状态和后果；可以很短，不为普通修复填模板。后续取代时旧ADR保留原理由并链接替代者，当前说明指向有效决定。ADR的决策谱系是持续用途，不适用“过时便删到Git历史”；普通临时材料仍按生命周期退出。无Git时不假设提交能恢复原件。

## 按变更维护与验证

采用 [Docs as Code](https://www.writethedocs.org/guide/docs-as-code/) 的同源文本、审查与现有检查，以及 [Google随变更更新和减少重复](https://google.github.io/styleguide/docguide/best_practices.html) 的做法；复用项目交付流程，不建立第二套文档票务、审批或发布链。无Git项目沿真实保存与恢复机制，不自动初始化；业务原件、凭据、数据库与原始日志不因此进入版本库。

重构前后核：独有事实及例外未丢；读者从实际入口按普通任务选路后能完成操作，必要条件无散落或反复入口跳转；同一行为变化只更新其主人及必要引用；现状/目标/历史可区分；工具和独立包仍消费正确来源；在途任务的固定业务、验收及外部操作基线受保护。结构、链接、场景消费与运行验证各自说明覆盖范围。没有观察数据不估算节省时间或Token，不以标准名称代替收益证据。

知识分类、层级和路径各有主人。步骤与参考如何编排、如何写触发指针，使用实际安装的 writing-for-agents；不在本参考复制一份写作教材。迁移和唯一收尾继续沿现有维护方法。
